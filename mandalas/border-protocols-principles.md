### The layout itself — from two rings to a force-directed cluster layout (same day)

The Composer then named the deeper issue: the graph's two concentric rings were borrowed wholesale from the Principles mandala's shape — but the Principles mandala is *unipartite* (principles↔principles) and this graph is *bipartite* (protocols↔principles). Forcing a bipartite graph into a unipartite graph's shape is a category error, and it's why a hand-rolled barycentre/exhaustive-search-rotation heuristic was needed at all: solving "how does a protocol orbit an already-fixed ring" instead of "where do these two node kinds actually want to sit." He also named the fix precisely: reorganize by proximity to *family* (cluster) and *linked principles*, and use real open-source graph-layout tooling instead of hand-computing — recalling the Graphviz Figma plugin as prior art.

**Researched, not guessed:** d3-force (pure physics simulation, ~30KB, position-calculation only), Graphviz-via-WASM (`@hpcc-js/wasm-graphviz` — the actual engine behind the Figma plugin, native DOT cluster support, but a real multi-hundred-KB binary and either a CDN fetch or vendoring), and Cytoscape.js (full framework, ruled out — it manages its own DOM/rendering, which would have meant rebuilding the hand-built accessibility layer — native `<title>` tooltips, keyboard focus, `wireFocus` isolation — rather than reusing it). Composer chose d3-force: smallest footprint, matches this page's existing "hand-authored, dependency-light" convention, replaces position calculation only.

**Vendored, not CDN-linked:** `project/qa/vendor/d3-force.vendored.js` — d3-force v3 + its three dependencies (d3-quadtree, d3-dispatch, d3-timer), combined and downloaded locally so the page keeps working offline, with a header documenting source URL and ISC licence.

**What changed, what didn't:** `clusterForceLayout()` (new helper) replaces the ring/barycentre code entirely — 6 principle-cluster anchors on an inner circle, 6 protocol-cluster anchors on an outer circle, every node pulled toward its own cluster's anchor while `forceManyBody` (repulsion), `forceLink` (warrant edges pull connected pairs together) and `forceCollide` (no overlap) do the real settling, run for 400 ticks and frozen. Every rendering, tooltip, keyboard-navigation, and hover-isolation line in `buildGraph`/`wireFocus` is **unchanged** — the swap touched position calculation only, exactly as scoped. `clusterLabels()` needed no modification either: it already worked from each node's `.cos`/`.sin` (unit direction from centre), which now come from the node's *true* settled angle instead of an assumed ring position — an existing helper turned out to already be general enough.

**Verified, not asserted:** 63/63 nodes valid (0 NaN positions), 60/60 edges render with 0 zero-length, 12 cluster-label groups (6 principle + 6 protocol, up from 6 protocol-only before). Real clustering, not cosmetic: average intra-cluster node distance 171px vs average inter-cluster distance 430px — a 2.5× separation ratio, measured on the rendered DOM, not assumed from the force parameters. Hover-isolation re-tested on a cluster label directly (dispatched a synthetic `mouseenter`): 16 nodes and 13 edges correctly went hot. Columns and Matrix forms (which don't use the force layout — they lay rows out by index) re-verified unaffected: 63/60 and 60-cell counts unchanged.

### Second pass, same day — the Composer read the rendered graph and found it wasn't actually more readable

Shown a screenshot of the force-both-sides layout, the Composer's answer was direct: no, not uniformly. Measured it rather than defending the first pass: **12 colliding label pairs** on the rendered DOM (bounding-box collision detection, not eyeballed), concentrated where the two node kinds converged near centre. Widening spacing brought it to 2–3 — but the count *changed between reloads of the identical page*, because the simulation reseeds its random jitter every run. A "verified zero collisions" claim that isn't reproducible isn't verified.

**The fix wasn't tuning the physics harder — it was a different design.** Two points from the Composer, stated together: (1) protocols and principles don't need the same treatment, because principles already have their own fully-labelled mandala one section up — this graph doesn't need to re-earn their legibility; (2) tools and math are a **visualization aid to inspect and judge, not a rule to obey blindly**. Applied: **protocols keep a plain deterministic ring** — the same technique `ring()` already gives every other graph on this page, ordered into contiguous cluster arcs (decision 6), zero label collisions *by construction*, not by tuning. **Principles go free-form** inside that ring, pulled toward their own Yin-cluster and toward whichever protocols warrant them (via `forceLink` against the protocols' now-fixed ring positions, pinned with `fx`/`fy`) — explicitly *not* required to be collision-free, because this isn't where they're meant to be read in full. A dashed white circle (`.principle-echo`, no fill, no data encoding) marks that free-form cluster as "the Principles mandala, folded small" — a pointer at section 1, not a second reading surface.

**Verified, twice — before and after a residual fix.** First measurement after the redesign: 34/34 protocol labels + 6 cluster labels, 0 collisions on that pass, but 2 protocol-vs-protocol collisions surfaced on inspection — both explainable, not random: `Independent Verification` / `Exploration & Play mute` sit at the ring's wrap-around seam (first and last cluster meeting near the top), and `Chamber / Echo / Antiphony` / `Instrument families` are same-cluster neighbours at the bottom — both cases long names landing in `ring()`'s middle-anchor zone, where a label extends both directions from its node instead of being pushed to one side. Fixed by widening the ring radius (620→760, more circumference per slot) rather than special-casing the anchor threshold. Re-measured, twice, across full page reloads: **0 protocol-label collisions both times** — and because protocol positions are now pure deterministic math (no randomness left on that side), this result doesn't depend on which random seed the principles happened to draw. Full-page regression re-run after every change: 7/7 graphs render, 0 console errors, the task-mandala switcher (built earlier the same day) still works, 0 dead-end spokes.

**One thing this pass surfaced about the check itself, not the graph:** the first "0 collisions" reading after the redesign was real but incomplete — it only measured what happened to be true on that load. Reproducibility (checked by reloading, not assumed from one clean run) is what turned "looked fine once" into a claim worth writing down.

### Third pass, same day — a ring of rings

Shown the second pass rendered, the Composer asked two more direct questions: *"Did you read protocols better than principles? Did you see their dots bigger?"* Checked rather than assumed: node radius is `r=13` for both — identical. Protocols read better purely from **spacing** (each on its own ring position with a clear label); principles are the same size, just packed tightly enough to overlap. Offered to size protocol dots up to reinforce the hierarchy directly. The Composer's answer was structurally sharper: *"What if it's the family of protocols who are in a ring, and protocols inside this family as a small circle? Fractal design to a fractal concept."*

**Applied:** `ringOfRings()` — the 6 protocol families positioned on a macro ring (the shape pass 2 already used), and each family's own members positioned on a *small ring centred on that family's own point* on the macro ring. The same shape, one level down — literally the fractal the orchestrator's own governance model already is (Principles↔Protocols↔Musicians), applied to how one graph draws itself rather than only to what it depicts. Built from `ring()` called twice — once for families, once per family — not new position math, because "the same rule, one level up" is what a fractal *is*; the code should read that way too. Mini-ring radius scales with member count (floored so 3-member families don't collapse); family labels sit past each mini-ring's own edge, on the same radial line the macro ring already put that family on.

**Two rounds of real bugs, not tuning — found and fixed in order:**
1. First render: 2 collisions, both a protocol's own label touching its family's label. Root cause: `.clabel`'s CSS default (`text-anchor:middle`) grows a label in *both* directions, including back toward the very mini-ring it names — node labels already avoid this with a direction-based anchor, family labels never got the same treatment. Fixed with the same anchor logic, inline.
2. Anchor fix alone wasn't enough — same class of collision persisted. Diagnosed properly this time: each mini-ring's members started at a fixed angle unrelated to which direction that family's own label pointed, so for a small family (3–5 members) one could land close enough to the label direction by chance regardless of radius. **First attempted fix was backwards** — rotating the gap to `+180°` put it toward the *global centre* and clustered members *toward* the label instead of away from it; caught immediately when collisions went from 2 to 5, not silently shipped. Corrected (no `+180`) and re-verified: 1 remaining, a 2px near-miss between `Knowledge-Pivot` and `Learning & Pattern` — measured as a real, if marginal, overlap (not assumed to be noise), closed by widening the label's radial push in three small, re-measured steps (72→95→140) until the actual bounding boxes cleared, not by guessing one big number.

**Verified, not asserted:** 0 protocol-label collisions across **three separate full-page reloads** after the final fix. Full-page regression re-run: 7/7 graphs render, 0 console errors, the task-mandala switcher still works, 0 dead-end spokes, 34 protocol + 29 principle nodes, 6 family labels.

**Why option 1 serves that vision specifically:** a warrant citation is a *directed* edge — it has a source and a target. One-to-one pairing yields undirected pairs; a coverage matrix yields undirected adjacency. Only a directed edge can express *subordination*, which is the containment the current flat ring cannot show. Every level of the fractal needs direction, or each level reproduces the same defect at a new scale.
